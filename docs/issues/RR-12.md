# RR-12: Design and implement one authenticated PostgreSQL slice

Status: open local draft; not a published GitHub issue.

Milestone: 6

Planned owner: @joewahy (B, your friend); reviewer: @lakerss6 (A). Recorded locally; not assigned on GitHub.

## Goal

Move one narrow feature, saved lists, behind authenticated workspace-scoped PostgreSQL persistence.

## Dependencies

Complete demo gate including RR-11; user agrees on auth provider and database setup

## Starting points

New database/auth layer; existing list storage boundary

## Acceptance criteria

- [ ] First propose auth provider, database setup, ORM choice, migration approach, and environment variables; ask before the dependent implementation.
- [ ] Create smaller child issues if this exceeds one reviewable slice.
- [ ] Implement users/workspaces/list ownership with server-side authorization on every operation.
- [ ] Test that user A cannot read/write user B lists by guessing IDs.
- [ ] Document migration, seed, backup/reset implications, and development setup without secrets.
- [ ] Retain a clearly separated synthetic demo mode; do not silently switch storage.
- [ ] Record follow-on issues for remaining entities, job queues, and approved production scheduling.

## Guided first steps for beginners

1. Start with a design discussion, not a database install: ask for an explanation of auth, workspaces, and migrations.
2. Choose setup with the user and split implementation into smaller child issues.
3. Implement one saved-list operation first, prove isolation between two users, then expand the slice.

Work on one step at a time. Ask for explanations or hints when stuck; the debugging exercise is a learning prompt, not a deliberately planted bug.

## Learning objective

Relational schema, migrations, authentication versus authorization, and integration tests.

## Debugging exercise

Call a list endpoint as a second user with the first user list ID; inspect and test the rejection.

## Verification and handoff

Run `npm run typecheck` and `npm run build`. Record relevant manual steps and any focused tests. Have the reviewer reproduce one edge case. Explain one implementation decision in your own words.

## Out of scope

Full production migration, live contact provider, live mailbox, public deployment.
