# RR-05: Create an explicit server-side demo email lookup

Status: open local draft; not a published GitHub issue.

Milestone: 3

Planned owner: @joewahy (B, your friend); reviewer: @lakerss6 (A). Recorded locally; not assigned on GitHub.

## Goal

Reveal an invented work address only after an explicit simulated lookup.

## Dependencies

Milestone 2; agree response contract with RR-06

## Starting points

New server provider module and lookup endpoint; public PersonSummary remains email-free

## Acceptance criteria

- [ ] Put email fixtures in a server-only module using reserved example.com/example.org domains.
- [ ] Initial public summaries and page payloads contain no email values.
- [ ] Use an explicit lookup mutation with validated person ID and a normalized result shape.
- [ ] Demonstrate pending, found, not_found, and failed outcomes with retry.
- [ ] Deduplicate active requests and label all verification results simulated.
- [ ] Do not make paid or live requests.

## Guided first steps for beginners

1. Draw the browser-to-server request and agree on the result fields with your partner.
2. Create a server-only synthetic lookup that handles one known ID and one missing ID.
3. Connect a clearly labeled simulated-lookup button, then add pending/error/retry behavior.

Work on one step at a time. Ask for explanations or hints when stuck; the debugging exercise is a learning prompt, not a deliberately planted bug.

## Learning objective

Server/client boundaries, input validation, async state, and provider adapters.

## Debugging exercise

Inspect network payloads before reveal and test double-clicking during a pending request.

## Verification and handoff

Run `npm run typecheck` and `npm run build`. Record relevant manual steps and any focused tests. Have the reviewer reproduce one edge case. Explain one implementation decision in your own words.

## Out of scope

Authentication, billing, real providers, or guaranteed delivery.
